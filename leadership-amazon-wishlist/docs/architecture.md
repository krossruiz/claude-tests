## Data Models

### Club

Stores club names so they can be selected from a dropdown in the request form and used as filter options.

| Field       | Type     | Notes                        |
|-------------|----------|------------------------------|
| `name`      | String   | Required, unique, trimmed.   |
| `createdAt` | Date     | Auto-generated by Mongoose.  |
| `updatedAt` | Date     | Auto-generated by Mongoose.  |

Clubs are created automatically when a request uses a new club name, or they can be created directly via the API.

### Request

Represents an order request submitted by a club member.

| Field                 | Type     | Notes |
|-----------------------|----------|-------|
| `clubName`            | String   | Required. |
| `personName`          | String   | Required. Name of the person submitting. |
| `message`             | String   | Required. Free-text details about the request. |
| `urgency`             | String   | Required. Either `"urgent"` or `"not-urgent"`. |
| `desiredDeliveryDate` | Date     | Required if urgency is `"urgent"`, otherwise null. |
| `status`              | String   | `"pending"` (default), `"confirmed"`, or `"rejected"`. |
| `items`               | Array    | Array of RequestItem subdocuments (at least one required). |
| `createdAt`           | Date     | Auto-generated by Mongoose. |
| `updatedAt`           | Date     | Auto-generated by Mongoose. |

### RequestItem (subdocument of Request)

Represents a single Amazon product within a request. Each item is tracked independently.

| Field                       | Type   | Notes |
|-----------------------------|--------|-------|
| `amazonUrl`                 | String | Required. Link to the Amazon product. |
| `quantity`                  | Number | Required. Defaults to 1, minimum 1. |
| `trackingUrl`               | String | Set by admin after ordering. Null by default. |
| `orderStatus`               | String | One of: `not_ordered` (default), `ordered`, `shipped`, `out_for_delivery`, `delivered`, `cancelled`, `returned`. |
| `deliveryEstimate`          | Date   | Populated by AI extraction or set manually. |
| `extractedInfo.itemName`    | String | Product name from the tracking page. |
| `extractedInfo.price`       | String | Price string (e.g., "$29.99"). |
| `extractedInfo.carrier`     | String | Shipping carrier name. |
| `extractedInfo.lastChecked` | Date   | Timestamp of the most recent AI extraction. |
| `extractedInfo.rawSummary`  | String | Brief AI-generated summary of order status. |

## Request Lifecycle

```
Club member submits request
         |
         v
     [ PENDING ]
         |
    Admin reviews
       /    \
      v      v
[CONFIRMED] [REJECTED]
      |
      | Admin places Amazon order and adds tracking URL
      v
  Items tracked individually:
  not_ordered -> ordered -> shipped -> out_for_delivery -> delivered
                                                       -> cancelled
                                                       -> returned
```

## AI Extraction Flow

When a tracking URL is added to an item (or re-extraction is triggered):

1. **Fetch** - The server fetches the tracking page HTML using `node-fetch`.
2. **Parse** - Cheerio strips scripts, styles, navigation, headers, and footers. The remaining body text is extracted and truncated to 8000 characters.
3. **Prompt** - The cleaned text is sent to the local Ollama instance with a structured prompt asking for a JSON response containing: item name, price, order status, delivery estimate, carrier, and a summary.
4. **Extract** - The server parses the JSON from Ollama's response. The `orderStatus` field is validated against the allowed values.
5. **Store** - Extracted fields are merged into the item's `extractedInfo` subdocument and saved to MongoDB. The `deliveryEstimate` and `orderStatus` fields on the item are also updated if the AI provides them.

If any step fails, the error is logged and the item's existing data is left unchanged.

## Background Polling

The `startOrderTracking()` function runs on a configurable interval (default 5 minutes). Each cycle:

1. Queries MongoDB for all requests that have items with a tracking URL and an active order status (`ordered`, `shipped`, or `out_for_delivery`).
2. For each matching item, runs the AI extraction flow described above.
3. Saves updated information back to the database.

Items with a terminal status (`delivered`, `cancelled`, `returned`) or no tracking URL are skipped.

## Frontend Architecture

The frontend is a set of static HTML pages served by Express from the `public/` directory. Each page has a corresponding JavaScript file that handles:

- Fetching data from the API.
- Rendering the UI by building HTML strings and setting `innerHTML`.
- Handling user interactions (form submissions, button clicks, dropdown changes).

There are no frontend build tools or frameworks. All client-side code is vanilla JavaScript using the Fetch API for HTTP requests. HTML is escaped via a `textContent`-based helper function to prevent XSS.

## Scripts

| Script        | Purpose |
|---------------|---------|
| `start.cmd`   | Starts MongoDB, Ollama, and the Node server. Saves process IDs to `.pids`. |
| `stop.cmd`    | Reads `.pids` and stops only the processes started by `start.cmd`. |
| `restart.cmd` | Runs stop logic, then calls `start.cmd`. |

The scripts use PowerShell's `Start-Process -PassThru` to capture PIDs and `taskkill /pid` to stop specific processes, ensuring other instances of `node.exe`, `mongod.exe`, or `ollama.exe` on the system are not affected.
